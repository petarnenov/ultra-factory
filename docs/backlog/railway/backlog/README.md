# Беклог: AO в Railway (ключ `RW`)

Източник: `../railway-report.md`. Вариант A: hub (BFF + daemon оркестратор) + daemon работници като Railway services.

## Структура
```
backlog/
  RW-1-rabotnik-v-railway/        епик   → EPIC.md
    RW-1.1-adr/                   стори  → STORY.md
      RW-1.1.1-adr-bff.md         таск   (събтасковете са чеклист в таска)
```
- **Епик** = фаза от отчета. **Стори** = цел, видима за потребител или оператор. **Таск** = една PR-размерна единица работа. **Събтаск** = чекбокс в таска.
- Всеки таск има: Цел, Контекст (файлове), Събтаскове, Критерии за приемане, Проверка, Оценка, Зависимости.
- Оценките са в човекодни (чд) за разработчик, който познава репото.

## Ред на изпълнение
| Епик | Съдържание | чд | Етап |
|---|---|---|---|
| RW-1 | Работник в Railway, управляван от desktop приложението | 6–9 | MVP-1 |
| RW-2 | Уеб UI + BFF в Railway | 11–18 | MVP-2 |
| RW-3 | Добавяне и махане на работници от UI | 5–8 | Пълна цел |
| RW-4 | Hardening, тестове, документация | 3–5 | Пълна цел |

Критичен път: RW-1.1 → RW-1.2 → RW-1.3 → RW-1.4 (валидира Railway) → RW-2.4 (BFF) → RW-3.

## Правила от репото, които всеки таск спазва
- `AGENTS.md` hard rules: loopback listener-ът остава `127.0.0.1` без auth. Нов network bind или неавтентикиран маршрут изисква ADR (`docs/adr/`).
- Всяко състояние на приложението е под `~/.ao` (`AO_DATA_DIR`). В контейнер това е volume-ът.
- CLI-ят е тънък клиент над daemon HTTP.
- Промени по API: `npm run api` регенерира OpenAPI спецификацията и TS типовете.
- Преди PR: `make check`.
