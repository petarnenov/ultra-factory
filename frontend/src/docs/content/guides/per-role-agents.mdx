---
title: Per-role agents
description: Configure separate harnesses and models for worker and orchestrator sessions.
---

Orchestrator has two session roles:

- A **worker** implements a focused task in an isolated workspace and may own pull requests.
- An **orchestrator** supervises a project, monitors sessions, and delegates implementation to workers.

Orchestrator can also run a dedicated reviewer against a worker's pull request. Reviewers run separately from worker and orchestrator sessions. See the [review loop](/guides/review-loop#ao-reviewer-agents) to choose a reviewer, start a run, and send findings to the worker.

Role and interface are separate choices. Either role can start in structured Chat or Terminal UI when its harness supports that interface.

## Configure roles

Open Project Settings in the desktop app and choose a coding agent for each role. The CLI can set these agents while registering a project:

```bash
ao project add --path /absolute/path/to/repo \
  --worker-agent codex \
  --orchestrator-agent claude-code
```

For a full configuration replacement, the stored JSON shape is:

```json
{
  "worker": {
    "agent": "codex",
    "agentConfig": {
      "model": "gpt-5.4",
      "permissions": "bypass-permissions"
    }
  },
  "orchestrator": {
    "agent": "claude-code",
    "agentConfig": {
      "model": "claude-opus-4"
    }
  }
}
```

This example uses `bypass-permissions`, which lets provider tools act without their normal approval prompts. Use it only when intended; available permission modes depend on the provider.

The `--config-json` flag takes a JSON string, not a file, and `set-config` replaces the whole project configuration. Preserve existing setup, rules, reviewers, and intake settings. See [Projects: update from the CLI](/configuration/projects#update-from-the-cli) for CLI limitations and safer alternatives.

## Choose which models a harness offers

Open **Settings → Harnesses**, choose a harness, and open **Models**. Turn a model's switch off to hide it from the model pickers for new tasks, project settings, reviewers, agent switching, and chat. **Enable all** and **Disable all** change every listed model at once; at least one model stays on. With every model on, the pickers offer the harness's full catalog, including models it reports later.

The choice belongs to the selected computer. A model a project, task, or session already uses stays listed even when it is switched off. Cloud VM tasks use their own catalog.

The Models tab also shows each model's context window in tokens when the harness catalog reports it.

## How harness, model, and effort resolve

Every launch resolves three values in the same order:

1. An explicit spawn directive: `--agent`/`--harness`, `--model`, and `--effort` (API: `harness`, `model`, `effort`).
2. Project Settings for the role on the machine that will run the agent.
3. That machine's harness default: the catalog's default model and, when it reports one, default effort.
4. Otherwise the launch is blocked.

An explicit harness does not discard the configured model or effort. If Project Settings select `opencode-v2` with `opencode/deepseek-v4.1-flash` and a spawn asks for `--agent opencode`, AO still applies the configured model and validates it for `opencode`. A value that harness cannot run blocks the spawn instead of silently starting on the harness's own default.

Project Settings are per machine. Harness availability, credentials, and model catalogs differ between computers, so each daemon resolves its own roles and validates against its own catalog. `ao spawn --host` therefore uses the target machine's Project Settings and harness defaults, not the caller's. A blocking error names that machine and lists its valid harnesses, the selected harness's valid models, and the valid effort levels for the selected model.

The same validation applies to reviewers: a reviewer model or effort configured in Project Settings must be valid for the reviewer harness on the target machine, or the review is blocked before it starts.

The resolved values and their source (`explicit`, `settings`, or `machine-default`) are recorded on the session, together with the machine whose configuration applied. `ao session get` shows them next to the harness, model, and effort.

## Start an orchestrator or worker

The desktop provides dedicated new-session and orchestrator flows. From the CLI:

```bash
ao spawn --project my-project --kind orchestrator \
  --name supervisor --mode chat

ao spawn --project my-project --kind worker \
  --name issue-42 --issue 42 --mode tui
```

`--name` is required and limited to 100 characters. Use `--harness`, `--model`, and `--effort` to direct one spawn explicitly. The daemon validates the combination before anything starts.

## Choose Chat or Terminal UI

- Use **Chat** for structured messages, provider activity, approvals, plans, changed files, usage, compaction, and rollback. Chat support depends on the harness and installed version; see the [agent capability catalog](/plugins/agents#chat-versus-terminal-ui).
- Use **Terminal UI** when you want the agent's native interface or a harness without native Chat support.

Compatible Claude Code and Codex sessions expose **Switch to chat UI** or **Switch to terminal UI**. Idle sessions switch directly. When work is active, Orchestrator asks whether to finish and drain it or stop and interrupt it before switching controllers.

The default interface comes from **Settings → General**. Project `agentConfig.mode` does not set Chat or Terminal UI. A choice made for a task or with the CLI takes precedence.

Model, reasoning effort, permissions, and provider execution modes depend on the selected agent. The configured model and effort follow whichever harness the spawn selects and are validated against it. Chat support and the ability to switch interfaces are separate capabilities, so use the switch action offered for that session.

## Project rules

Use `agentRules` and `agentRulesFile` for worker instructions. Use `orchestratorRules` for supervision-specific guidance. These are stored in the typed project config and injected into the appropriate session role.

	Orchestrator uses the provider CLI already installed and authenticated on your machine. Run `ao doctor` if a configured harness fails preflight.
</Callout>
